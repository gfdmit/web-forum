# web-forum

Бэкенд веб-форума, написанный на Go с использованием микросервисной архитектуры. Система состоит из четырёх независимых сервисов — API Gateway, Auth Service, Post Service и Media Service — каждый из которых развёртывается в отдельном Docker-контейнере и взаимодействует с остальными через внутреннюю сеть.

## Архитектура

```
                        ┌─────────────────────┐
                        │     API Gateway      │
                        │     :8080            │
                        └──────────┬──────────┘
                                   │
               ┌───────────────────┼───────────────────┐
               │                   │                   │
    ┌──────────▼──────┐  ┌─────────▼──────┐  ┌────────▼────────┐
    │   Auth Service   │  │  Post Service  │  │  Media Service  │
    │   :4000          │  │  :3000         │  │  :2000          │
    └─────────────────┘  └────────┬───────┘  └────────┬────────┘
                                  │                   │
                         ┌────────▼───────┐  ┌────────▼────────┐
                         │   PostgreSQL   │  │      MinIO      │
                         │   :5432        │  │   :9000         │
                         └────────────────┘  └─────────────────┘
```

Все сервисы подключены к выделенной Docker bridge-сети (`app-network`). API Gateway — единственный сервис, который пробрасывает порт на хост; остальные сервисы взаимодействуют исключительно внутри сети.

---

## Сервисы

**api-gateway** — обратный прокси и единственная точка входа для всех внешних запросов. Маршрутизирует трафик к нужному нижестоящему сервису, выполняет проверку аутентификации и скрывает внутреннюю топологию от клиентов.

**auth-service** — отвечает за регистрацию пользователей, вход в систему, выдачу и валидацию JWT-токенов. В качестве хранилища использует PostgreSQL.

**post-service** — управляет постами форума (создание, чтение, обновление, удаление). Сохраняет данные в PostgreSQL; запускается только после того, как база данных перейдёт в состояние healthy.

**media-service** — обрабатывает загрузку файлов и хранение медиаконтента. Использует MinIO в качестве S3-совместимого объектного хранилища.

## Начало работы

### Клонирование репозитория

```bash
git clone https://github.com/gfdmit/web-forum.git
cd web-forum
```

### Настройка переменных окружения

В корне репозитория находится файл `example.env`, а в каждой директории сервиса ожидается свой `.env`-файл, который Docker Compose подхватывает через директиву `env_file`. Начните с копирования корневого примера:

```bash
cp example.env .env
```

Затем создайте конфигурацию для каждого сервиса:

```bash
# Post Service
cp example.env post-service/.env

# Auth Service
cp example.env auth-service/.env

# Media Service
cp example.env media-service/.env

# API Gateway
cp example.env api-gateway/.env
```

При необходимости отредактируйте значения в каждом файле. Полный список переменных см. в разделе [Переменные окружения](#переменные-окружения).

### Запуск через Docker Compose

Собрать образы и запустить все сервисы в фоновом режиме:

```bash
make build
# или без make:
docker compose up -d --build
```

При первом запуске Docker соберёт все четыре образа. Последующие запуски через `make up` используют кешированные образы:

```bash
make up
```

После запуска API доступно по адресу:

```
http://localhost:8080
```

Остановить и удалить контейнеры:

```bash
make down
```

Остановить и удалить контейнеры **и** все именованные тома (данные PostgreSQL и MinIO):

```bash
make down_clear
```

## Справочник по Makefile

| Цель                    | Описание                                                                    |
|-------------------------|-----------------------------------------------------------------------------|
| `make up`               | Запустить все контейнеры в фоновом режиме без пересборки                    |
| `make build`            | Собрать образы и запустить все контейнеры в фоновом режиме                  |
| `make restart`          | Остановить все контейнеры и запустить их снова без пересборки               |
| `make rebuild`          | Остановить контейнеры, пересобрать образы и запустить снова                 |
| `make rebuild_clear`    | То же, что `rebuild`, но также удаляет все персистентные тома               |
| `make down`             | Остановить и удалить все контейнеры                                         |
| `make down_clear`       | Остановить и удалить все контейнеры и именованные тома                      |

## Переменные окружения

Корневой `example.env` определяет следующие переменные. Индивидуальный `.env` каждого сервиса наследует или переопределяет их по необходимости.

| Переменная            | Значение по умолчанию | Описание                                                          |
|-----------------------|-----------------------|-------------------------------------------------------------------|
| `POSTSERVICE_PORT`    | `3000`                | Порт, на котором слушает Post Service                             |
| `AUTHSERVICE_PORT`    | `4000`                | Порт, на котором слушает Auth Service                             |
| `MEDIASERVICE_PORT`   | `2000`                | Порт, на котором слушает Media Service                            |
| `APIGATEWAY_PORT`     | `8080`                | Порт, который API Gateway пробрасывает на хост                    |
| `MINIO_PORT`          | `9000`                | Порт MinIO                                                        |
| `POSTGRES_USER`       | `postgres`            | Имя суперпользователя PostgreSQL                                  |
| `POSTGRES_DB`         | `postgres`            | Имя базы данных по умолчанию                                      |
| `POSTGRES_PORT`       | `5432`                | Порт PostgreSQL                                                   |
| `MINIO_USER`          | `minioadmin`          | Корневой пользователь MinIO (access key)                          |
| `MINIO_PASSWORD`      | `minioadmin`          | Пароль корневого пользователя MinIO (secret key). Смените в продакшене. |

> **Внимание:** Не коммитьте `.env`-файлы с реальными учётными данными в систему контроля версий. Значения по умолчанию предназначены исключительно для локальной разработки.

## Структура проекта

```
web-forum/
├── api-gateway/
│   ├── deploy/
│   │   └── Dockerfile
│   └── ...                  # Исходный код Gateway
├── auth-service/
│   ├── deploy/
│   │   └── Dockerfile
│   └── ...                  # Исходный код Auth Service
├── media-service/
│   ├── deploy/
│   │   └── Dockerfile
│   └── ...                  # Исходный код Media Service
├── post-service/
│   ├── deploy/
│   │   └── Dockerfile
│   └── ...                  # Исходный код Post Service
├── .github/
│   └── workflows/           # Конфигурация CI на GitHub Actions
├── docker-compose.yaml      # Оркестрация всех сервисов
├── example.env              # Эталонный файл переменных окружения
├── Makefile                 # Вспомогательные make-цели
└── README.md
```

Каждый сервис самодостаточен: он владеет своим `Dockerfile` в директории `deploy/`, собственным Go-модулем и собственным `.env`. Это позволяет собирать и деплоить сервисы независимо друг от друга.

## CI/CD

Репозиторий содержит конфигурацию GitHub Actions в директории `.github/workflows/`. Пайплайн запускается при пушах и пул-реквестах в ветку `main` и, как правило, выполняет следующие шаги:

- Линтинг кода
- Запуск юнит- и интеграционных тестов
- Проверку сборки Docker-образов

За точным описанием шагов и триггеров обращайтесь непосредственно к YAML-файлам воркфлоу.

## Участие в разработке

1. Сделайте форк репозитория.
2. Создайте ветку для новой функциональности: `git checkout -b feature/your-feature`.
3. Зафиксируйте изменения в стиле conventional commits.
4. Запушьте ветку в свой форк и откройте пул-реквест в `main`.
5. Убедитесь, что все проверки CI проходят, прежде чем запрашивать ревью.

Issues и пул-реквесты приветствуются.
